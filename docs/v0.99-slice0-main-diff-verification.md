# v0.99 slice 0 — the constraint, tested against `main` for the first time

**Question.** The branch's governing constraint is *no athlete-visible visual
change*, with four recorded exceptions. Has that been tested? No. The branch's
pixel-diff evidence used `.screenshots/slice0-final/` as its baseline, and that
directory was captured **after** the token commits landed. Every capture on the
branch is post-token, so the diff compared one task's output against another
task's output. It says nothing about the delta from `main`.

This report captures `main` and compares it, surface by surface.

## 1. Exactly what was compared to what

This is the crux, so it is stated before any number.

| | baseline | subject |
| --- | --- | --- |
| commit | `2da5f83` (`main`) | `9196ecd` (`v0.99-the-app-you-can-read`) |
| worktree | detached worktree, outside the repo tree | `/home/vscode/recover` |
| dev server | `localhost:3200` | `localhost:3100` |
| database | dev Postgres `5435` (`recover-devdb`) — **the same database** | same |
| account | `demo@recover.local`, owner, seeded | same |
| rendered state | `:root`, **no `.dark` class** | `.dark`, applied by `ThemeProvider` |

**What "dark" means on `main`.** `main` has no `.dark` class anywhere. Its single
`:root` block *is* the dark theme (`--background: #0a0a0a`), and `next-themes` is
a dependency it never imports. So `main` has exactly **one** renderable state,
and that state is what every athlete on `main` sees.

Two consequences, both load-bearing:

1. **The baseline was captured with no `.dark` class on the document.** `main`
   *does* already ship `@custom-variant dark (&:is(.dark *))`, so if the capture
   script had toggled `.dark` on — as it does on the branch — it would have
   switched on the 11 `dark:` utilities that are dead code on `main`. That would
   have silently erased recorded exception 2 from the diff. The baseline script
   was patched to assert `.dark` is **absent** and that `body` computes
   `rgb(10, 10, 10)`, and to refuse to capture otherwise.
2. **Light mode is not comparable and is excluded.** `main` has no light theme
   to compare against, and on the branch light mode is unreachable by the
   athlete (`forcedTheme="dark"`). There is no athlete-visible light-mode delta
   because there is no athlete-visible light mode. Every number in this report is
   about the one state an athlete can actually reach.

So the comparison is: **`main`'s only rendered state vs the branch's dark state**
— i.e. what an athlete saw before this branch vs what an athlete sees after it.
That is the only comparison the constraint is about.

**The instrument.** `main` has no `scripts/verify-surfaces.ts`; the branch's was
copied in. It is the instrument, not the subject. Its refusal to run without
`SCREENSHOT_BASE_URL` and its refusal of port 3000 were left intact. Four
adaptations were made to the **copy in the main worktree only**, each marked
`BASELINE ADAPTATION` in that file:

1. dropped the `src/lib/design/{contrast,tokens}` imports — branch-only files;
2. `EXPECTED_BODY_BACKGROUND` hardcoded to `rgb(10, 10, 10)`, `main`'s `:root`
   `--background`, since there is no token module to read it from;
3. `forceThemeVerified` **does not toggle the class** and asserts its absence
   (reason 1 above);
4. the theme loop runs once, not twice. Output files are still labelled `-dark-`
   purely so they pair 1:1 with the branch's dark captures by filename.

No source file on the branch was changed. `.screenshots/` is gitignored, so this
report carries the findings rather than PNGs.

## 2. What the CSS says should change (arithmetic, before looking)

The branch touches 28 files; only five can move a pixel: `src/app/globals.css`,
`src/app/layout.tsx`, `src/components/theme-provider.tsx`,
`src/app/train/page.tsx`, `src/components/train/fitness-tiles.tsx`. That bounds
the search.

`main`'s translucent tokens are composited against its own ground to get a
comparable rendered value. White at alpha *a* over `#0a0a0a` renders as

Contrast arithmetic on the two that matter most, against `--surface-base`:

- `--border`: rgb(34) on rgb(10) is **1.24:1** — a whisper. rgb(107) on rgb(10)
  is **3.71:1**. Borders become roughly three times as contrasty.
- `--muted-foreground`: rgb(108) on rgb(22) (`--card`) is **3.77:1**; rgb(138) on
  rgb(22) is **5.24:1**. This reproduces the prior review's 3.8→5.2 figure.

`--border` reaches every element through `@layer base { * { @apply border-border } }`,
so it repaints wherever any border-width is set and no explicit colour overrides
it. `.glass` sets its own border from `--glass-border`, which is preserved, so
glass cards are **not** affected — this is why the change is not uniform and why
looking was necessary.

`src/app/layout.tsx` also changes `themeColor` from a single `#0a0a0a` to a
`prefers-color-scheme` pair. That is browser-chrome colour, not page pixels, so
no screenshot can show it; it is analysed in §5.

Two surfaces are **not comparable by pixels at all**:

- **`admin`** renders live, per-run mutable data (session list, sync-job queue,
  security-event log, surface views). Its self-diff is 39 015 px with maxΔ 233 —
  the *same* transition families (`22,22,22 ↔ 245,245,245`, `104 ↔ 22`) that
  dominate its main-vs-branch diff. Its 74 065 px main-vs-branch figure is
  therefore mostly data, not code.
- **`settings-token-created`** self-diffs at 44–52% **and changes height between
  two runs of identical code** (2431 → 2595 px), because every run creates
  another API token and the token string differs each time. No pixel percentage
  from this surface means anything. It is assessed by eye only.

For every other surface the noise floor is 0–379 px against main-vs-branch
diffs of 513–8 288 px, so those differences are real signal.
