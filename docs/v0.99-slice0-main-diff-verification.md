# v0.99 slice 0 — the constraint, tested against `main` for the first time

**Question.** The branch's governing constraint is _no athlete-visible visual
change_, with four recorded exceptions. Has that been tested? No. The branch's
pixel-diff evidence used `.screenshots/slice0-final/` as its baseline, and that
directory was captured **after** the token commits landed. Every capture on the
branch is post-token, so the diff compared one task's output against another
task's output. It says nothing about the delta from `main`.

This report captures `main` and compares it, surface by surface.

## 1. Exactly what was compared to what

This is the crux, so it is stated before any number.

|                | baseline                                                      | subject                                  |
| -------------- | ------------------------------------------------------------- | ---------------------------------------- |
| commit         | `2da5f83` (`main`)                                            | `9196ecd` (`v0.99-the-app-you-can-read`) |
| worktree       | detached worktree, outside the repo tree                      | `/home/vscode/recover`                   |
| dev server     | `localhost:3200`                                              | `localhost:3100`                         |
| database       | dev Postgres `5435` (`recover-devdb`) — **the same database** | same                                     |
| account        | `demo@recover.local`, owner, seeded                           | same                                     |
| rendered state | `:root`, **no `.dark` class**                                 | `.dark`, applied by `ThemeProvider`      |

**What "dark" means on `main`.** `main` has no `.dark` class anywhere. Its single
`:root` block _is_ the dark theme (`--background: #0a0a0a`), and `next-themes` is
a dependency it never imports. So `main` has exactly **one** renderable state,
and that state is what every athlete on `main` sees.

Two consequences, both load-bearing:

1. **The baseline was captured with no `.dark` class on the document.** `main`
   _does_ already ship `@custom-variant dark (&:is(.dark *))`, so if the capture
   script had toggled `.dark` on — as it does on the branch — it would have
   switched on the 14 `dark:` utilities (21 occurrences, 4 files — count
   corrected by I3) that are dead code on `main`. That would
   have silently erased recorded exception 2 from the diff. The baseline script
   was patched to assert `.dark` is **absent** and that `body` computes
   `rgb(10, 10, 10)`, and to refuse to capture otherwise.
2. **Light mode is not comparable and is excluded.** `main` has no light theme
   to compare against, and on the branch light mode is unreachable by the
   athlete (`forcedTheme="dark"`). There is no athlete-visible light-mode delta
   because there is no athlete-visible light mode. Every number in this report is
   about the one state an athlete can actually reach.

So the comparison is: **`main`'s only rendered state vs the branch's dark state**
— i.e. what an athlete saw before this branch vs what an athlete sees after it.
That is the only comparison the constraint is about.

**The instrument.** `main` has no `scripts/verify-surfaces.ts`; the branch's was
copied in. It is the instrument, not the subject. Its refusal to run without
`SCREENSHOT_BASE_URL` and its refusal of port 3000 were left intact. Four
adaptations were made to the **copy in the main worktree only**, each marked
`BASELINE ADAPTATION` in that file:

1. dropped the `src/lib/design/{contrast,tokens}` imports — branch-only files;
2. `EXPECTED_BODY_BACKGROUND` hardcoded to `rgb(10, 10, 10)`, `main`'s `:root`
   `--background`, since there is no token module to read it from;
3. `forceThemeVerified` **does not toggle the class** and asserts its absence
   (reason 1 above);
4. the theme loop runs once, not twice. Output files are still labelled `-dark-`
   purely so they pair 1:1 with the branch's dark captures by filename.

No source file on the branch was changed. `.screenshots/` is gitignored, so this
report carries the findings rather than PNGs.

**Name corrected by the rendered pass (§6.4).** This row said `.nav-dot`, which
is not a class that exists — not on `main`, not on the branch, not anywhere in
the repo's history (`git log -S'nav-dot'` returns only the commit that wrote this
row). The rule is `.nav-active-dot`, `globals.css:389`, applied by
`bottom-nav.tsx:43`. The observation was right and the identifier was invented;
§6.4 confirms the change renders, on five surfaces.

Contrast arithmetic on the two that matter most, against `--surface-base`:

- `--border`: rgb(34) on rgb(10) is **1.24:1** — a whisper. rgb(107) on rgb(10)
  is **3.71:1**. Borders become roughly three times as contrasty.
- `--muted-foreground`: rgb(108) on rgb(22) (`--card`) is **3.77:1**; rgb(138) on

so it repaints wherever any border-width is set and no explicit colour overrides
it. `.glass` sets its own border from `--glass-border`, which is preserved, so
glass cards are **not** affected — this is why the change is not uniform and why
looking was necessary.

`src/app/layout.tsx` also changes `themeColor` from a single `#0a0a0a` to a
`prefers-color-scheme` pair. That is browser-chrome colour, not page pixels, so
no screenshot can show it; it is analysed in §5.

### 6.2 The two dominant families, confirmed as predicted

- **`250,250,250 → 245,245,245`** is the largest transition on 14 of 18
  surfaces (peak 52 918 px on admin-phone, 3 509 px on activity-log-phone). This

- **`~108–115 → 138`** appears on activity-log, login, train, import, coach,

  ("EMAIL ADDRESS") and train ("THIS WEEK'S AVAILABILITY", "RACES"): the

### 6.3 The finding the token diff could not have predicted

`settings-token-created` cannot be diffed by pixels, so it was reached through
the real UI on both servers and the success box was screenshotted on its own.

**On `main`, the newly-created API token is invisible.**

|                  | token text         | its background     | ratio      |
| ---------------- | ------------------ | ------------------ | ---------- |
| `main` `2da5f83` | `rgb(250,250,250)` | `rgb(255,255,255)` | **1.02:1** |
| branch `33cd77e` | `rgb(245,245,245)` | `rgb(0,0,0)`       | ~19:1      |

`main`'s own axe run confirms it independently and reproducibly — the one
`confirmed` node in the entire 20-capture baseline, on both viewports:

> `.break-all` — insufficient color contrast of **1.04** (foreground `#fafafa`,
> background `#ffffff`, 12px). Expected 4.5:1.

The branch has **0 confirmed nodes across all 20 dark captures.**

Mechanism, and why no token could show it: `api-tokens-card.tsx`'s success box
carries `bg-green-50`/`bg-white` for light and `dark:bg-green-950`/`dark:bg-black`
for dark. `main` never applies `.dark`, so the box rendered its **light** styles
while the surrounding app was dark, putting near-white token text on a white
`<code>` block. Activating those four dead utilities — recorded exception 2 — is
what fixes it. This is a Tailwind-variant activation interacting with a
component's light-mode defaults; it is not a token value, so it is absent from
the 15-row table by construction.

The consequence is not cosmetic. The box says _"Copy this token now — it won't be
shown again"_, and on `main` there is nothing legible to copy and no second
chance. **Exception 2 is disclosed as a change, but nowhere is it recorded that
what it fixes is an athlete-blocking WCAG failure on `main`.** That severity is
this report's contribution, not the plan's.

### 6.4 `.nav-active-dot` — a 16th rendered change, in no exception

The active bottom-nav dot changes, and it is **not** among the 15 token values
and **not** in any of the four recorded exceptions.

`globals.css:389` moves `background`/`box-shadow` from the bare keyword `white`
to `var(--ink-primary)`, i.e. `#ffffff → #f5f5f5` on a 4px dot **and its 12px
glow**. Confirmed rendered on **five phone surfaces** — today, train, coach, body
and settings (the dot follows the active route) — cropped and looked at on all
five: dot core `254→243` (coach), `253→237` (train), `247→228` (body),
`245→234` (settings), each visibly very slightly dimmer, same size and position.

Three reasons this is a genuine gap rather than a technicality:

1. The constraint says dark mode changes "in exactly the 15 token values in the
   table below, **and nowhere else**." This is somewhere else.
2. It is not a token, so the token-arithmetic method that produced the 15 could
   not have found it — and the branch's own CSS comment admits the first
   `globals.css` scan "could not see it at all (C1)" because it enumerated two
   `rgba()` spellings and the token hexes, not bare keywords.
3. §2's table did list it, but under `.nav-dot` — **a class that does not exist**
   (see the correction there). So the one place it was written down named the
   wrong thing, and the authoritative 15-row constraint omits it.

Classified **expected but not disclosed**. It moves the right way (a white dot on
a light surface would be an invisible active-nav indicator) and 10/255 on a 4px
dot is below any plausible perceptual threshold — this is a bookkeeping gap, not
a regression.

## 9. Verdict

**The rendered evidence CONFIRMS `docs/dark-mode-delta-vs-main.md` and EXTENDS
it. It does not contradict it.**

Confirmed: every token delta that reaches a captured surface renders as the
arithmetic predicted, in the predicted direction, and nothing rendered worse than
`main`. The document's own closing caveat — that a rendered capture was still
owed — is now discharged.

Extended, in five ways the token diff could not have reached:

1. **No layout shift on any of the 18 comparable surfaces** (§6.1) — identical
   dimensions, every band a recolour in place. The explicitly-flagged blind spot
   is clean.
2. **`main` shipped an invisible API token at 1.04:1** and exception 2 is what
   fixes it (§6.3) — the strongest single piece of evidence that this branch
   improves the app, and it was in nobody's list.
3. **A 16th undisclosed rendered change**, `.nav-active-dot` (§6.4), which no
   token-based method could find.
4. **`color-scheme` and `themeColor` are at parity with `main`** (§7), settled by
   DOM probe rather than argument; the two post-`9196ecd` commits work.
5. **Two headline pixel counts are substantially not code** (§6.5) — settings'
   biggest band is a session counter, body's whole floor is an animation phase.

The one place the rendered pass **corrects** rather than extends the record is
scope, not direction: exception 2's "every text field in the app" is false
(§8), and the 15-value table names two components that do not exist. Both are
bookkeeping defects in the disclosure, and both make the exception sound broader
than it is — the opposite of an undisclosed change.

**Bottom line for the constraint.** As written — "dark mode changes in exactly
the 15 token values, and nowhere else" — it remains **false**, now for a
sixteenth reason (`.nav-active-dot`) that survives at HEAD. As
`docs/dark-mode-delta-vs-main.md` recommends, the fix is to make the list
truthful rather than to revert: every rendered difference measured here moves
toward the goal, one of them fixes a WCAG failure that made a one-time secret
unreadable, and none of them moved a pixel of layout.
