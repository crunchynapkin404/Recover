# v0.53 Design: Planning Surface Parity Lock

Date: 2026-08-07
Status: Draft (ready for implementation)

## Problem

The planning surface state now spans multiple dimensions (`planStyle`, `seasonMode`, `reentryStage`).
Those values are exposed in several places (tools and train UI) and are vulnerable to drift if each path derives effective values independently.

## Goal

Introduce one shared effective-state contract used by all planning read/write surfaces so that:

- `effectiveStyle`
- `effectiveSeasonMode`
- `reentryStage`

are always consistent for the same stored constraints.

## Non-Goals

- No changes to week materialization algorithms.
- No changes to adaptation or safety precedence.
- No schema migrations.
- No visual redesign.

## Design Overview

1. Add a shared resolver module that:

- normalizes style
- normalizes season state
- returns one effective-state object

2. Use the resolver in:

- planning read tools (`get_week_plan`, `get_training_plan`)
- planning update tool responses (`update_training_plan`)
- train planning surface derivation path

3. Add parity tests that enforce identical outputs for identical constraints.

## Data Contract

Input: plan constraints object (or null).

Output:

- `effectiveStyle`: `balanced | block_lite`
- `effectiveSeasonMode`: `normal | off_season`
- `reentryStage`: `none | week_1 | week_2`

Normalization rules:

- Missing/unknown values fall back to existing defaults.
- `seasonMode=normal` forces `reentryStage=none`.

## Acceptance Criteria

- Tool outputs report identical effective-state fields for identical constraints.
- UI displays effective planning state from shared resolver, not local re-derivation.
- Existing materialization/adaptation tests remain green without behavior deltas.
- Full verification gate passes: format, typecheck, tests, build.

## Risks and Mitigations

- Risk: accidental behavior drift from touching planning service paths.
- Mitigation: isolate changes to derivation/serialization boundaries; add targeted parity tests; run existing week-plan test suites.

## Rollback

If parity lock introduces regressions, revert resolver adoption commit(s) while keeping v0.52 season-mode logic intact.
