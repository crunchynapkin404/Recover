# v0.49 - Fuelling Lite

## Why this release exists

Breadth starts here. After v0.42 through v0.48 closed correctness and cockpit
work, the largest practical gap is training-aware fuelling guidance.

This release ships deterministic, session-linked fuelling guidance that is
small, clear, and safe. It is not a nutrition app.

## Product goal

For each planned key workout, show a simple fuelling card the athlete can use
immediately:

- pre-session carbs
- during-session carbs and fluid
- post-session recovery carbs and protein

All guidance is range-based and confidence-labeled.

## Scope

### In scope

1. Fuelling card on Train surfaces for planned sessions and same-day workouts.
2. Deterministic fuelling rules based on:
   - planned duration
   - planned intensity band
   - athlete body mass when available
3. Three guidance blocks:
   - before workout
   - during workout
   - after workout
4. Confidence label and one-line rationale on each card.
5. Coach parity:
   - coach tool and coach response use exactly the same fuelling output.

### Out of scope

1. Meal logging and calorie tracking.
2. Micronutrients and supplement protocols.
3. AI-generated recipe plans.
4. Race-day course-specific nutrition execution.
5. New integrations.

## Data and rules

### Inputs

1. Planned session duration minutes.
2. Planned session intensity band.
3. Athlete body mass from existing profile data when present.

### Deterministic rule set

1. Short, easy sessions: light fuelling recommendation.
2. Moderate or long sessions: pre and during carbs increase by duration band.
3. Hard sessions: emphasize pre and post recovery windows.
4. If body mass is missing, show conservative generic ranges and mark
   confidence lower.

### Confidence model

- high: duration + intensity + body mass present
- medium: duration + intensity present, no body mass
- low: missing planned intensity or session shape

## UX

1. Mobile-first fuelling card in Train week view and session detail.
2. One-tap readability:
   - no hidden wizard
   - one screen, one answer
3. Card text must name assumptions explicitly.

## Safety constraints

1. Never output exact claims dressed as certainty when anchors are missing.
2. Never block training plan generation when fuelling is unavailable.
3. Fuelling output is advisory only and cannot change planned targets.

## Acceptance criteria

1. Planned sessions with duration and intensity render a fuelling card.
2. Card shows before/during/after guidance and confidence label.
3. Same input session always yields the same output.
4. Coach output for fuelling matches UI output for same session.
5. Missing body mass degrades gracefully and visibly.
6. No migrations required.
7. Existing planning and adaptation tests remain green.

## Concise implementation outline

### 1) Deterministic rules (single shared engine)

Add one pure module that converts session inputs to a canonical fuelling result:

- input: `durationMins`, `intensityBand`, `bodyMassKg?`
- output: `before`, `during`, `after`, `confidence`, `rationale[]`, `assumptions[]`

Closed, table-driven rules (no model inference):

1. Duration band:
   - short: `< 60 min`
   - medium: `60-90 min`
   - long: `> 90 min`
2. Intensity band:
   - easy, moderate, hard
3. Guidance:
   - before carbs:
     - short/easy: `20-30 g`
     - medium/moderate: `30-60 g`
     - long/hard: `1.0-1.5 g/kg` (fallback `60-90 g` if mass missing)
   - during carbs:
     - short/easy: `0-20 g/h`
     - medium/moderate: `30-45 g/h`
     - long/hard: `60-90 g/h`
   - during fluid:
     - short: `400-600 ml/h`
     - medium/long: `500-900 ml/h`
   - after recovery (within 1-2h):
     - carbs: `0.8-1.2 g/kg` (fallback `60-90 g` if mass missing)
     - protein: `20-40 g`
4. Confidence:
   - high: duration + intensity + body mass
   - medium: duration + intensity
   - low: missing intensity or invalid session shape

All numbers are deterministic constants in code comments + tests.

### 2) Minimal additive code changes

Prefer adding new modules/components over refactoring existing planning flow.

1. Add `src/lib/fuelling-lite.ts`
   - `buildFuellingGuidance(input): FuellingGuidance`
   - pure functions only; no db, no network
2. Add `src/lib/fuelling-lite.test.ts`
   - band boundaries and confidence matrix
3. Add `src/components/train/fuelling-card.tsx`
   - dumb presentational card for before/during/after + confidence + rationale
4. Update `src/components/train/week-day-list.tsx`
   - render card only for rows with planned workout(s) in scope
   - if needed, show first key workout on a day in v0.49 (explicitly defer multi-workout aggregation)
5. Add/extend `src/components/train/week-day-list.test.tsx`
   - card render, missing-mass fallback, and no-card states
6. Add coach tool `src/lib/tools/get-fuelling-guidance.ts`
   - calls the same `buildFuellingGuidance` helper
7. Register tool in `src/lib/tools/registry.ts`
   - no changes to existing tool signatures

No schema migration. No plan generation logic changes. No adaptation behavior changes.

### 3) Coach parity contract

Parity means UI and coach never re-implement rules separately.

1. Shared canonical shape exported from `fuelling-lite.ts`
2. UI card receives canonical shape directly
3. Coach tool returns the same shape (or a strict superset with presentation text)
4. Parity test asserts deep equality for same fixture input across:
   - UI derivation path
   - coach tool derivation path

### 4) Focused test strategy

1. Unit (rule engine):
   - duration boundary tests: `59`, `60`, `90`, `91`
   - intensity mapping tests: easy/moderate/hard
   - body-mass present vs missing fallbacks
   - deterministic invariant: identical input => identical output
2. Component (Train card):
   - renders before/during/after blocks
   - confidence badge text and rationale
   - assumption copy appears when body mass missing
3. Tool parity:
   - `get-fuelling-guidance.test.ts` verifies tool output equals direct engine output
4. Non-regression gates:
   - keep existing suite unchanged
   - run targeted tests first, then full gates (`lint`, `typecheck`, `test`, `build`)

### 5) Rollout order (small, safe)

1. Ship engine + unit tests.
2. Ship Train card behind existing session availability conditions.
3. Ship coach tool wired to same engine.
4. Ship parity + regression tests.

## Verification

1. Unit tests for rule bands and confidence assignment.
2. Component tests for card rendering and missing-input states.
3. Tool tests for coach parity.
4. Full regression gates:
   - npm run lint
   - npm run typecheck
   - npm run test
   - npm run build

## Risks

1. Overprecision language can create false trust.
2. Incomplete session metadata can reduce useful coverage.
3. Scope creep into full nutrition tracking.

## Non-goal guardrail

If a proposal requires persistent food logs, it is out of scope for v0.49 and
must be deferred.
