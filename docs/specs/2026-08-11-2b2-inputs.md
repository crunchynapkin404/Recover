# Phase 2b.2 — the inputs, measured

**Not a design spec.** 2b.2 is a brainstorm → spec → plan cycle and this
document decides nothing. It is the evidence pack that cycle starts from, so
the brainstorm argues about the IA rather than about what the tree currently
contains. Everything here was measured on 2026-08-11 at v0.96.0; every count
names the mechanism that recomputes it, because this item's history is a
history of counts going stale in prose.

## What 2b.2 has to decide

From `docs/ROADMAP.md`: _decide what the IA now is, dispose of the orphaned
components, and make the directory tree match._ The gate that held it until
2026-09-05 was lifted on 2026-08-11 (v0.95.0).

## Evidence 1 — what the athlete actually opens

`surface_views`, the local-only telemetry v0.66.0 shipped for exactly this
decision. Deployed live 2026-08-08, read 2026-08-11.

| Surface        | Views | Days seen |
| -------------- | ----: | --------: |
| `today`        |    69 |         4 |
| `train`        |    53 |         4 |
| `body`         |    31 |         4 |
| `coach`        |    13 |         4 |
| `settings`     |     8 |         3 |
| `admin`        |     3 |         2 |
| `activity`     |     0 |         — |
| `activity-log` |     0 |         — |
| `import`       |     0 |         — |

**Three caveats bind on this table and none of them is optional.**

1. **`import`'s zero means nothing.** It is a once-ever surface — connect a
   provider and never return. It would read zero over any window. Do not
   conclude it is unused.
2. **`activity` and `activity-log`'s zeros do mean something.** Four
   activities were recorded inside the window and the athlete never opened
   either surface. That is behaviour, not a quiet week. It is still only four
   days of it.
3. **The counts are developer-biased and n=1.** The sole user is also the
   developer, so this shows what was being built. It answers "which surfaces
   does the only athlete open" and supports **no** claim about athletes in
   general. If a second user ever joins, this reading expires.

## Evidence 2 — the IA as built

Nav (`src/components/sidebar-nav.tsx`) is five items:

| Label | Route       |
| ----- | ----------- |
| Today | `/`         |
| Train | `/train`    |
| Coach | `/coach`    |
| Body  | `/body`     |
| Menu  | `/settings` |

Routes with no nav entry: `/admin`, `/import`, `/activity/[id]`,
`/activity/log`, `/join/[code]`, `/login`, and `/wellness` — a seven-line
redirect stub to `/body?tab=journal` kept for old bookmarks.

The telemetry's closed set (`src/lib/telemetry.ts`'s `SURFACES`) is the nine
authenticated surfaces. `login` and `join/[code]` are pre-auth with no user to
attribute; `/wellness` renders nothing and forwards to a page that records.

## Evidence 3 — the tree does not match the IA, in two different ways

`src/components/` still carries the pre-v0.23 directories. The count that
matters is not the dead one:

| Retired dir  | Total | Dead | **Live, needs a home** |
| ------------ | ----: | ---: | ---------------------: |
| `dashboard/` |    14 |    9 |                      5 |
| `plan/`      |    14 |    3 |                     11 |
| `log/`       |     6 |    1 |                      5 |
| `journal/`   |     2 |    1 |                      1 |
| `health/`    |     5 |    0 |                      5 |
| **Total**    |    41 |   19 |                 **27** |

**27 live components sit in directories the v0.23 IA retired** — more than the
22 dead ones. `health/` is the sharpest case: nothing in it is dead, and the
whole directory is live code at an address the IA no longer has.

This reframes the item. "Remove the orphans" is the smaller half; the larger
half is that a third of the component tree is filed under an IA that stopped
existing in v0.23, and every future reader navigates that tree.

### The disposal list — 22, and do not retype it

The authority is `KNOWN_ORPHANS` in `tests/dead-component-guard.test.ts`. The
guard recomputes reachability on every run and fails if the list drifts, in
either direction. Earlier figures in `ROADMAP.md` (12, and 19 counting "PR
#86's seven sleep-cards") were wrong in both directions: five of those seven
sleep-cards no longer exist and the two that remain are live, while the true
count was **higher** than anything written down.

v0.96.0 rebuilt the guard on reachability from entry points and found 7 the
old "is anything referencing it" question structurally could not see: six were
alive only because a _dead_ component imported them, in chains up to three
deep, and `dashboard/vitals-grid.tsx` looked referenced because
`today/vitals-grid.tsx` shares its basename.

## Traps this cycle should expect

- **Reachability marks a _file_ dead, not every symbol in it.** v0.87.0 hit
  this: `dashboard/race-countdown.tsx` could not be deleted wholesale because
  it exported the type `app/train/page.tsx` imported. The type moved to
  `race/outlook.ts` and then the component went. Expect more — an orphan may
  own a type, a constant or a style something live still imports.
- **Deleting an orphan can orphan its neighbour.** The chains are real: remove
  `hero-readiness.tsx` and `readiness-rings.tsx`, `hero-card.tsx` and then
  `animated-counter.tsx` fall behind it. The guard now handles this
  automatically, but the _count_ will move as deletions land.
- **`journal/correlation-insights.tsx` is allowlisted twice** — here and in
  `tests/uncertainty-dialects-guard.test.ts`. Deleting it touches both.
- **Some orphans may be worth reviving, not deleting.** That is the whole
  reason this waited for usage data. `dashboard/calibration-progress.tsx` is
  cited in the 2b.3 spec as the model for the `calibrating` state — and it is
  live, in a retired directory.
- **Three vendored `ui/` primitives** (`separator`, `sonner`, `tabs`) are
  unused. The guard deliberately declines the "exempt `ui/` wholesale"
  argument. Whether an unused primitive is debt or inventory is a real
  question, not a foregone one.

## Adjacent, found while measuring — not 2b.2's

Three **non-component** files are also unreachable from any entry point and
live only for their own tests: `lib/week-plan/repair.ts`,
`lib/workout-export/week.ts`, `lib/workout-export/zwo.ts`. The last two form a
cluster whose only non-test consumer is each other, which suggests an
unshipped feature rather than debris. The dead-component guard covers
`src/components/**` only, so nothing currently watches this. Recorded here so
it is not lost; disposition belongs to Phase 4, not to 2b.2.

## Open questions for the brainstorm

None of these are answered here on purpose.

1. **Is the five-item nav still right?** Telemetry says `coach` gets 13 views
   to `today`'s 69. That is the ranking under a developer's usage during a
   release week.
2. **What happens to `activity` and `activity-log`?** They are reachable only
   by drilling in, and were not visited in four days that contained four
   activities. Demote, merge into `train`, or leave?
3. **Where do the 27 live components go?** Straight `dashboard/`→`today/`,
   `plan/`→`train/`, `health/`+`journal/`+`log/`→`body/` is the obvious
   mapping and probably wrong in places — `log/pmc-chart.tsx` and
   `log/fitness-stats-row.tsx` serve Train's Fitness tab, not Body.
4. **Does the directory tree mirror the IA at all?** An alternative is
   organising by domain rather than by surface, which would make the question
   moot and the migration permanent instead of recurring. This is the second
   time the tree has drifted from the IA.
5. **Delete or revive, per orphan?** 22 decisions, and the roadmap explicitly
   allows revival.
6. **Does `/wellness` finally go?** Old bookmarks are the only argument for
   it, and the instance has one user who can be asked.
