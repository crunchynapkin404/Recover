# Multi-A-race seasons (v0.114.0) — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an athlete plan a season around **two** A-races — a full arc to
the first, an evidenced recovery bridge, a rebuild, and a correct taper for the
second — instead of a plan that ends at race one.

**Architecture:** `periodize()` stops producing one Base→Build→Peak→Taper arc
and starts composing segments: `arc(weeksToFirstRace) + recovery(n) +
arc(remainingWeeks)`, where `arc()` is today's body moved unchanged and
`recovery(n)` reuses `PLAN_CONSTANTS.RECOVERY_FRACTION`. The second race is
**explicit** — supplied by the caller, never inferred — and stored in one
additive nullable column pair so every existing plan row behaves bit-identically.

**Tech Stack:** TypeScript, Next.js (App Router), Drizzle ORM + Postgres,
Vitest, Zod (MCP tool parameters), Tailwind + the v0.99 token scale.

**Spec:** `docs/specs/2026-08-19-multi-a-race-implementation-design.md`
**Evidence:** `docs/specs/2026-08-19-multi-a-race-transition-evidence.md`
(every number below traces to this) and
`docs/specs/2026-08-19-taper-evidence.md` (the taper numbers it reuses).

```ts
/**
 * Days of recovery a race of this class costs before rebuilding may start.
 *
 * **Evidence:** `docs/specs/2026-08-19-multi-a-race-transition-evidence.md`.
 *
 * Note the asymmetry with the taper windows directly above, because it is
 * easy to assume they behave the same way and they do not. Ferreira et al.
 * 2023 pooled middle-, long- and ultra-distance and found **no significant
 * difference by event distance** for taper LENGTH — so that mapping is a
 * convention the evidence tolerates. Recovery is the opposite: distance is
 * exactly where it shows up. Marathon aerobic capacity is back inside 7 days
 * (Takayama et al. 2017, n=11); an Ironman still shows significantly elevated
 * CK, myoglobin, IL-6 and hs-CRP at 5 days (Neubauer et al. 2008, n=42) and
 * took 15 days for VO2max in the one case study (Nosaka et al. 2010, n=1); a
 * 166 km ultra needs 9-16 days for neuromuscular function (Millet et al.
 * 2011). **The same classifier is a tolerated convention for the taper and a
 * supported one for the recovery.**
 *
 * Read the confidence per row, not the table shape. Only the long class has
 * studies under it.
 */

/**
 * Marathon / full Ironman. Bounded BELOW by marathon aerobic recovery at 7d
 * and ABOVE by Ironman VO2max at 15d, with inflammation still significant at
 * 5d. Aerobic capacity returns before tissue does, and a plan that resumes on
 * the aerobic reading alone resumes onto a leg that is still repairing — so
 * this sits above the marathon finding and below the Ironman one.
 * Confidence: Medium. A judgement between two evidenced endpoints, which is
 * not the same as a number with no endpoints.
 */
export const RACE_RECOVERY_DAYS_LONG = 14;

/**
 * Half / 70.3 / fondo / century. **No study was located at this distance** —
 * a search on 2026-08-19 returned CK kinetics reported second-hand and no
 * primary time-to-recovery study in trained runners. Interpolated between the
 * long class and nothing. Confidence: Low.
 */
export const RACE_RECOVERY_DAYS_MID = 7;

/**
 * Everything else. **Invented** — no evidence at all. A floor so a short
 * A-race still costs something rather than nothing. Confidence: Low.
 */
export const RACE_RECOVERY_DAYS_SHORT = 4;

export function raceRecoveryDays(raceType: string): number {
  const window = taperWindowDays(raceType);
  if (window === TAPER_WINDOW_LONG) return RACE_RECOVERY_DAYS_LONG;
  if (window === TAPER_WINDOW_MID) return RACE_RECOVERY_DAYS_MID;
  return RACE_RECOVERY_DAYS_SHORT;
}
```

Note it delegates to `taperWindowDays` rather than re-matching the strings —
that is what makes the fourth test true by construction instead of by luck.

- [ ] **Step 4: Compose in `periodize()`**

```ts
export function periodize(opts: PeriodizeOptions): Block[] {
  const first = opts.firstRace ?? null;
  if (!first) return arc({ ...opts, weeks: opts.weeksTotal });

  const recoveryWeeks = Math.ceil(raceRecoveryDays(first.raceType) / 7);
  const rebuildWeeks = opts.weeksTotal - first.weekNumber - recoveryWeeks;

  const segments = [
    arc({ ...opts, weeks: first.weekNumber }),
    recoverySegment({ ...opts, weeks: recoveryWeeks }),
    arc({ ...opts, weeks: rebuildWeeks }),
  ].flat();

  // Contiguous renumbering. Both live sites (week-plan/service.ts:393,
  // week-plan/project.ts:239) find their block by matching a number against
  // weekNumber and FALL BACK TO THE LAST BLOCK when the match misses — so a
  // gap here does not throw, it silently serves the plan's final week.
  return segments.map((b, i) => ({ ...b, weekNumber: i + 1 }));
}
```

**The segments must hand fitness to each other, and this is the part most
likely to go wrong.** `arc()` takes `startingCtl`. If you pass the plan's
original `startingCtl` to the second `arc()`, the rebuild restarts from the
athlete's **pre-season** fitness — they would finish a marathon and be handed a
Base week sized for the person they were four months earlier. Three values have
to flow:

1. **Into `recoverySegment`:** the load basis is the **last block of arc 1**
   (`arc1[arc1.length - 1].targetLoad`), scaled by `PC.RECOVERY_FRACTION`. Not
   `hoursPerWeek`, and not the plan's starting load.
2. **Into arc 2's `startingCtl`:** the CTL implied by where recovery leaves
   them — `recoveryLoad / PC.CTL_TO_WEEKLY_LOAD`, the documented inverse
   (`plan-constants.ts`: "a steady weekly load L settles at CTL = L/7").
3. **`startingTsb`** is a plan-start concept; pass `null` for arc 2.

Pin the handoff with its own test, because a wrong basis here produces a plan
that looks structurally perfect and is prescriptively absurd:

```ts
it("rebuilds from post-race fitness, not from plan-start fitness", () => {
  const blocks = periodize({
    ...base,
    startingCtl: 30,
    firstRace: { weekNumber: 10, raceType: "marathon" },
  });
  const lastOfArcOne = blocks[9].targetLoad;
  const firstOfRebuild = blocks[12].targetLoad;
  // The rebuild starts near where the athlete actually is after recovery,
  // not back at a CTL-30 Base week.
  expect(firstOfRebuild).toBeGreaterThan(lastOfArcOne * 0.4);
});
```

`recoverySegment` emits `weeks` blocks at `phase: "recovery"` and
`targetLoad = Math.round(basis * PC.RECOVERY_FRACTION)`. **Reuse** the existing
recovery-week construction inside `arc()` (around
`src/lib/training-plan.ts:460`) rather than writing a second one — verbatim
duplication of that block is a defect, not compliance. If the shape does not
factor out cleanly, extract the shared piece and call it from both.
