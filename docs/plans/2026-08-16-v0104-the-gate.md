# v0.104.0 — the gate between the boxes — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put a tested gate between a release tag and the athlete's live
instance, so every release is soaked on the dev box before prod can run it.

**Architecture:** `release.yml` already publishes pre-release tags without moving
`:latest` (metadata-action's `latest=auto` excludes them), and `:latest` is the
only tag prod's watchtower follows. So a `-rc.N` tag becomes a staging channel
for free. Devbox stands that exact image up under its own compose project, soaks
it, and a new `promote.yml` retags the **tested digest** to `:latest` without
rebuilding. Alongside: the release-critical gaps the topology review found —
prod's unbacked secrets, the app's missing healthcheck, and the fact that image
rollback does not roll the schema back.

**Tech Stack:** Docker Compose, GitHub Actions, `docker buildx imagetools`, GHCR,
watchtower, Postgres 16, drizzle-kit, Next.js 16 standalone, vitest,
playwright-core + headless Chromium, gpg, ssh.

**Spec:** `docs/specs/2026-08-16-dev-prod-gate-design.md`

## Global Constraints

  Never commit to `main` directly.
- **dev box:** `devbox`, 10.0.10.50. Repo at `/home/bart/projects/recover`.

- [ ] **Step 1: Write the failing test**

Create `tests/release-gate.test.ts`:

```typescript
// tests/release-gate.test.ts — v0.104.0's guardrail.
//
// The release gate is not a mechanism; it is an ABSENCE. `release.yml`
// publishes a pre-release tag without moving `:latest` only because
// docker/metadata-action's `latest` flavor is left at its default `auto`,
// which excludes pre-releases. Nothing in the repository says so. One later
// edit — `flavor: latest=true`, or a hand-written `-t …:latest` — silently
// re-arms the straight-to-prod path that this release exists to close, and
// no test would fail.
//
// So this scans the workflow files themselves. It is the same reasoning that
// put the `verify` job into release.yml after v0.63.0 and v0.64.0 were both
// tagged from commits whose CI had already failed: a written rule that
// nothing enforces is a rule that gets broken by accident.
//
// Comments are stripped before scanning. release.yml's own prose says
// "semver + auto `:latest`", and a naive substring scan would match it and
// fail on a correct file.
import { describe, expect, it } from "vitest";
import { readdirSync, readFileSync } from "node:fs";
import { join } from "node:path";

const WORKFLOWS = join(process.cwd(), ".github", "workflows");

function stripComments(yaml: string): string {
  return yaml
    .split("\n")
    .map((line) => line.replace(/(^|\s)#.*$/, ""))
    .join("\n");
}

function workflow(name: string): string {
  return stripComments(readFileSync(join(WORKFLOWS, name), "utf8"));
}

function allWorkflowNames(): string[] {
  return readdirSync(WORKFLOWS).filter(
    (f) => f.endsWith(".yml") || f.endsWith(".yaml")
  );
}

describe("release gate", () => {
  it("release.yml never forces the latest flavor", () => {
    const body = workflow("release.yml");

    expect(
      /latest\s*=\s*true/.test(body),
      "release.yml sets `latest=true`, which makes docker/metadata-action tag " +
        "EVERY release — including a -rc.N pre-release — as :latest. That is " +
        "the only tag prod's watchtower follows, so it deploys release " +
        "candidates straight to the athlete. Remove it; the default `auto` " +
        "already excludes pre-releases."
    ).toBe(false);

    expect(
      /type\s*=\s*raw\s*,\s*value\s*=\s*latest/.test(body),
      "release.yml hand-writes a raw :latest tag, which bypasses the " +
        "pre-release exclusion the gate depends on."
    ).toBe(false);
  });

  it("promote.yml is the only workflow that writes :latest", () => {
    const writers = allWorkflowNames().filter((name) =>
      /:latest/.test(workflow(name))
    );

    expect(
      writers,
      "Exactly one workflow may write the :latest tag — promote.yml, which " +
        "retags a digest already soaked on the dev box. Any other writer is " +
        "an undocumented path to production."
    ).toEqual(["promote.yml"]);
  });

  it("promote.yml promotes by digest and never rebuilds", () => {
    const body = workflow("promote.yml");

    expect(body).toContain("imagetools create");
    expect(
      /build-push-action|docker\s+build/.test(body),
      "promote.yml builds an image. Promotion must retag the digest that was " +
        "soaked, not produce a new one — a rebuilt image is not the artifact " +
        "that was tested."
    ).toBe(false);
  });
});
```

- [ ] **Step 3: Create `.github/workflows/promote.yml`**

```yaml
name: Promote

# Promotion is the ONLY thing that moves :latest, and therefore the only thing
# that deploys to the athlete's instance (prod's watchtower polls :latest every
# 300s). It retags a digest that was already built, published and soaked on the
# dev box as a -rc.N pre-release — it never builds. A rebuilt image is not the
# artifact that was tested, and `npm ci` resolution plus base-image drift are
# exactly the risks a soak exists to eliminate.
#
# Rollback uses this same workflow: dispatch it with rc_tag set to a previous
# release's tag. Read docs/RELEASING.md first — rolling the image back does not
# roll the schema back.

on:
  workflow_dispatch:
    inputs:
      rc_tag:
        description: "Tested tag to promote, e.g. 0.104.0-rc.1"
        required: true
        type: string
      release_tag:
        description: "Release tag to publish alongside :latest, e.g. 0.104.0"
        required: true
        type: string

env:
  IMAGE_NAME: ghcr.io/${{ github.repository_owner }}/recover

permissions:
  contents: read
  packages: write

jobs:
  promote:
    runs-on: ubuntu-latest
    steps:
      - uses: docker/setup-buildx-action@v3

      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Record the digest :latest points at now
        run: |
          set -euo pipefail
          before=$(docker buildx imagetools inspect "$IMAGE_NAME:latest" \
            --format '{{.Manifest.Digest}}' 2>/dev/null || echo none)
          echo "ROLLBACK_DIGEST=$before" >> "$GITHUB_ENV"
          echo "::notice title=Rollback target::$before — record this in docs/ENVIRONMENTS.md"

      - name: Promote the soaked digest
        run: |
          set -euo pipefail
          rc="$IMAGE_NAME:${{ inputs.rc_tag }}"
          digest=$(docker buildx imagetools inspect "$rc" --format '{{.Manifest.Digest}}')
          echo "::notice title=Promoting::$rc is $digest"
          docker buildx imagetools create \
            -t "$IMAGE_NAME:latest" \
            -t "$IMAGE_NAME:${{ inputs.release_tag }}" \
            "$IMAGE_NAME@$digest"

      - name: Verify :latest moved to exactly that digest
        run: |
          set -euo pipefail
          after=$(docker buildx imagetools inspect "$IMAGE_NAME:latest" --format '{{.Manifest.Digest}}')
          want=$(docker buildx imagetools inspect "$IMAGE_NAME:${{ inputs.rc_tag }}" --format '{{.Manifest.Digest}}')
          if [ "$after" != "$want" ]; then
            echo "::error::promotion did not land — :latest is $after, expected $want"
            exit 1
          fi
          echo "::notice title=Promoted::latest = $after (was $ROLLBACK_DIGEST)"
          echo "Now run scripts/live-verify-deploy.sh $after on devbox."
```

### Task 8: Bring prod's dumps and secrets to devbox

Two gaps at once. The dumps exist only on prod, on the same LXC as the database
they protect; and they are only half a restore, because `ENCRYPTION_KEY` — which
encrypts connector tokens at rest — lives only in prod's `.env`. Restore the
rows without the key and every connector token is permanently undecryptable.

**Files:**

- Create: `scripts/live-dump-sync.sh` (untracked — `.gitignore` excludes
  `scripts/live-*.sh` so a public clone never carries this instance's topology)
- Create: `~/.recover-backup-passphrase` on devbox (untracked, outside the repo)

**Interfaces:**

- Produces: docker volume `recover-dev_backups` holding prod's newest dump, and
  `~/recover-secrets/prod-env.gpg`. Task 9 consumes both.

- [ ] **Step 1: Create the passphrase file**

```bash
openssl rand -base64 32 > ~/.recover-backup-passphrase
chmod 600 ~/.recover-backup-passphrase
```

**Write this passphrase down somewhere that is neither box.** It is what makes
the encrypted `.env` recoverable if devbox is lost too, and it protects the copy
if it ever travels further. It does not protect against devbox itself being
compromised — the passphrase sits on the same machine as the ciphertext. That is
a deliberate trade for unattended operation, and it is stated so nobody mistakes
this for stronger than it is.

- [ ] **Step 2: Write `scripts/live-dump-sync.sh`**

```bash
#!/usr/bin/env bash
# Pulls prod's newest nightly dump and its (encrypted) .env to this box.
#
# Two jobs, both of which the nightly pg_dump on prod does not do:
#   1. A second copy of the dump, on a different LXC from the database it
#      protects.
#   2. A copy of prod's ENCRYPTION_KEY, without which a restored dump is rows
#      nobody can decrypt — every connector token in it is dead. The dump and
#      this file are two halves of one restore.
#
# Untracked on purpose (.gitignore: scripts/live-*.sh): it names this
# instance's hosts, and a public clone must not carry them.
#
# Usage: scripts/live-dump-sync.sh
set -euo pipefail

PROD_HOST="${PROD_HOST:-PROD}"
VOLUME="${RECOVER_BACKUP_VOLUME:-recover-dev_backups}"
SECRETS_DIR="${HOME}/recover-secrets"
PASSPHRASE_FILE="${HOME}/.recover-backup-passphrase"

fail() { echo "sync: FAIL — $*" >&2; exit 1; }

[ -r "$PASSPHRASE_FILE" ] || fail "no passphrase file at $PASSPHRASE_FILE"

STAGE=$(mktemp -d)
trap 'rm -rf "$STAGE"' EXIT

echo "sync: finding prod's newest dump"
NEWEST=$(ssh -o BatchMode=yes "$PROD_HOST" \
  'docker exec recover-backup-1 sh -c "ls /backups/recover-*.dump 2>/dev/null | sort | tail -n 1"') \
  || fail "could not list prod's dumps"
[ -n "$NEWEST" ] || fail "prod has no dumps in /backups"
BASE=$(basename "$NEWEST")

echo "sync: pulling $BASE"
ssh -o BatchMode=yes "$PROD_HOST" "docker exec recover-backup-1 cat '$NEWEST'" > "$STAGE/$BASE" \
  || fail "could not read $NEWEST"
[ -s "$STAGE/$BASE" ] || fail "$BASE arrived empty"

echo "sync: landing it in volume $VOLUME"
docker volume create "$VOLUME" >/dev/null
docker run --rm -v "$VOLUME":/backups -v "$STAGE":/stage:ro alpine \
  sh -c "cp /stage/'$BASE' /backups/ && ls -la /backups" >/dev/null \
  || fail "could not copy into $VOLUME"

echo "sync: pulling prod's .env, encrypted at rest here"
mkdir -p "$SECRETS_DIR"
chmod 700 "$SECRETS_DIR"
ssh -o BatchMode=yes "$PROD_HOST" 'cat /opt/stacks/recover/.env' \
  | gpg --batch --yes --symmetric --cipher-algo AES256 \
        --passphrase-file "$PASSPHRASE_FILE" \
        --output "$SECRETS_DIR/prod-env.gpg" \
  || fail "could not fetch or encrypt prod's .env"
chmod 600 "$SECRETS_DIR/prod-env.gpg"

echo "sync: OK — $BASE in $VOLUME, secrets in $SECRETS_DIR/prod-env.gpg"
```

### Task 10: Verify that a promotion actually landed

`promote.yml` runs on GitHub's runners, which cannot reach 10.0.10.100. So it
can succeed while prod sits on the old digest — watchtower wedged, poll
misconfigured, pull failing. Nothing would say so.

**Files:**

- Create: `scripts/live-verify-deploy.sh` (untracked, `live-*` convention)

**Interfaces:**

- Consumes: a digest string, `sha256:…`, printed by `promote.yml`.
- Produces: exit 0 only when prod is running that digest and reports healthy.

- [ ] **Step 1: Write the script**

```bash
#!/usr/bin/env bash
# Confirms prod is actually running the digest that was promoted.
#
# promote.yml runs on GitHub's runners, which cannot reach 10.0.10.100 — so it
# can go green while prod stays on the old image. This is the closing step of a
# release, and the first thing that would have caught 2026-08-07, when the app
# was healthy on its IP while the tunnel served 502s.
#
# Usage: scripts/live-verify-deploy.sh sha256:<digest>
set -euo pipefail

WANT="${1:?usage: live-verify-deploy.sh sha256:<digest>}"
PROD_HOST="${PROD_HOST:-PROD}"
PROD_URL="${PROD_URL:-http://10.0.10.100:3000}"
TIMEOUT_S="${TIMEOUT_S:-420}"

fail() { echo "verify: FAIL — $*" >&2; exit 1; }

echo "verify: waiting for prod to run $WANT (watchtower polls every 300s)"
deadline=$((SECONDS + TIMEOUT_S))
running=""
while [ "$SECONDS" -lt "$deadline" ]; do
  running=$(ssh -o BatchMode=yes "$PROD_HOST" \
    "docker inspect recover-app-1 --format '{{index .RepoDigests 0}}'" 2>/dev/null | sed 's/.*@//')
  [ "$running" = "$WANT" ] && break
  sleep 20
done
[ "$running" = "$WANT" ] || fail "prod is running ${running:-nothing}, expected $WANT"
echo "verify: digest matches"

state=$(ssh -o BatchMode=yes "$PROD_HOST" \
  "docker inspect recover-app-1 --format '{{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}}'")
case "$state" in
  healthy) echo "verify: container healthy" ;;
  none)    echo "verify: WARNING — no healthcheck on this container (pre-v0.104.0 stack file)" ;;
  *)       fail "container health is '$state'" ;;
esac

health=$(curl -fsS --max-time 10 "$PROD_URL/api/health") || fail "/api/health unreachable"
echo "$health" | grep -q '"status":"ok"' || fail "/api/health not ok: $health"
echo "$health" | grep -q '"db":"up"'     || fail "database not up: $health"
echo "$health" | grep -q '"backupAgeS":null' && fail "backupAgeS is null — see Task 7"

echo "verify: OK — $health"
```

````markdown
## Rolling back

Dispatch **Promote** again with `rc_tag` set to the previous release's tag
(digests and versions are in `docs/ENVIRONMENTS.md`). Watchtower picks it up
within 300s; confirm with `scripts/live-verify-deploy.sh`.

**This restores the code, not the schema.** `drizzle/` is forward-only and
`scripts/migrate.mjs` runs on every boot, so once a release with a migration has
started on prod, the database is permanently ahead of any older image. Check
step 5's classification for the release you are rolling back **past**:

- Only additive migrations since the target → retag and you are done.
- Any destructive migration since the target → the image rollback alone leaves a
  broken instance. Restore the newest dump into prod's database first, accepting
  the loss back to 03:30, and only then retag.
````
